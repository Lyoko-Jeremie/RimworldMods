# ArtificialMaid 深海通行设计方案

## 目标

让 `ArtificialMaid` 能主动寻路并实际走过原版不可通过地形，重点是 `WaterOceanDeep`、`WaterDeep`、`ToxicWaterOceanDeep`、`ToxicWaterDeep` 这类 `TerrainDef.passability = Impassable` 的深水/深海水格子。

该能力应只作用于人造人女仆，不应让普通 Pawn、动物、敌人或全局地形都变得可通行。

## rimsage 查询到的原版实现细节

### 地形与 PathGrid

`Verse.AI.PathGrid.CalculatedCostAt(IntVec3 c, ...)` 是静态通行成本的核心入口：

- 先读取 `map.terrainGrid.TerrainAt(c)`。
- 如果地形为空，或 `terrainDef.passability == Traversability.Impassable`，直接返回 `10000`。
- `10000` 是 `PathGrid.ImpassableCost`，`PathGrid.Walkable(...)` 判断条件是成本 `< 10000`。
- 只有当前 `PathGridDef.flying == true` 且 `terrainDef.forcePassableByFlyingPawns == true` 时，原版才允许飞行 Pawn 忽略不可通过地形。
- 建筑/物品如果 `ThingDef.passability == Impassable`，同样会让格子返回 `10000`，除非是飞行网格且该 ThingDef 有 `forcePassableByFlyingPawns`。

原版 `PathGridDef`：

- `Normal`: `fencePassable=true`, `flying=false`
- `FenceBlocked`: `fencePassable=false`, `flying=false`
- `Flying`: `fencePassable=true`, `flying=true`

水地形查询结果：

- `WaterShallow`：不是不可通过，`pathCost=30`，有 `Walkable` affordance。
- `WaterMovingChestDeep`：不是不可通过，`pathCost=42`，有 `Walkable` affordance。
- `WaterDeep`：`passability=Impassable`，`pathCost=300`，有 `forcePassableByFlyingPawns=true`。
- `WaterOceanDeep`：`passability=Impassable`，`pathCost=300`，没有查到 `forcePassableByFlyingPawns=true`。
- `ToxicWaterDeep` / `ToxicWaterOceanDeep`：`passability=Impassable`，`pathCost=400`，没有查到 `forcePassableByFlyingPawns=true`。

结论：`race.waterCellCost` 或基因的 `waterCellCost` 只能改变水格成本，不能把 `PathGrid` 已经判定为 `10000` 的深水变成可走。它适合浅水/齐胸流水，不适合深海水。

### 寻路、可达性与实际移动

原版有三层检查，必须全部覆盖：

1. `Reachability.CanReach(...)`
   - `PathRequest.Validate()` 会先做可达性验证。
   - `Reachability` 内部用 `map.pathing.For(traverseParams).pathGrid` 判断可达性。
   - `Pathing.For(TraverseParms)` 原版只在 `FenceBlocked` 和 `Normal` 之间选择，不会自动使用 Pawn 的自定义 `PathingContext`。

2. `PathFinder` / `PathGridJob`
   - `PathFinderMapData.ParameterizeGridJob(...)` 给 `PathGridJob.pathGridDirect` 赋值时，原版只会选择 `normalCost` 或 `fenceBlockedCost`。
   - 即使新增一个 `PathGridDef`，原版 A* 网格任务也不会自动使用它。
   - `PathGridJob.CellIsPassable(...)` 要求 `pathGridDirect[index] < 10000`，`PathRequest.IPathGridCustomizer` 只能额外加成本或阻挡，不能把原本 `10000` 的格子变成可通行。

3. `Pawn_PathFollower`
   - `SetupMoveIntoNextCell()` 会调用 `nextCell.WalkableBy(pawn.Map, pawn)`，这里通过 `map.pathing.For(pawn)` 判断实际下一格能不能进入。
   - `StartPath(...)` 里还有一个硬编码预检查：`map.reachability.CanReach(position, dest, peMode, TraverseParms.For(TraverseMode.PassDoors))`。这个检查没有 Pawn 参数，所以深水分割区域时会提前失败。
   - 当前项目已经 patch 了 `Pawn_PathFollower.CostToMoveIntoCell(Pawn, IntVec3)`，让 `ArtificialMaid` 移动不受地形成本影响；这只影响走路耗时，不解决深海水不可通行。

## 可选方案

### 方案 A：全局修改深水地形

做法：

- XML Patch 把 `WaterOceanDeep`、`WaterDeep`、`ToxicWaterOceanDeep`、`ToxicWaterDeep` 的 `passability` 改成可通行，或者复制一套可通行地形并替换地图地形。

优点：

- 实现最简单，几乎不需要 C#。
- 原版寻路、可达性和移动都会自然生效。

缺点：

- 全局影响所有 Pawn，不符合“只有 ArtificialMaid 可以走”的目标。
- 会影响基地布局、动物、敌袭、掉落、建筑放置、地图生成后的区域划分等大量系统。
- 不推荐。

### 方案 B：把 ArtificialMaid 当作飞行 Pawn

做法：

- 尝试让女仆持续处于 `Pawn.Flying == true`，走原版 `PathGridDefOf.Flying`。
- 或给相关深水地形补 `forcePassableByFlyingPawns=true`。

优点：

- 可以复用部分原版飞行逻辑。

缺点：

- `WaterOceanDeep` 和毒深水默认并没有 `forcePassableByFlyingPawns=true`。
- 原版 `PathFinderMapData.ParameterizeGridJob(...)` 仍然主要喂 normal/fence grid，不能保证 A* 对飞行网格完整生效。
- 飞行状态会牵连动画、阴影、落地、陷阱、碰撞、`Pawn_FlightTracker`、`MaxFlightTime`、`FlightCooldown` 等系统，语义上也不等同于“在深海上行走”。
- 不推荐作为主方案。

### 方案 C：为 ArtificialMaid 增加专用 PathGrid，并用 Harmony 接入三层检查

这是推荐方案。

核心思路：

- 新增 `PathGridDef`：例如 `ArtificialMaidPathGrid`。
- 新增 `ArtificialMaidPathGrid : PathGrid`。
- 只在 `ArtificialMaid` 的可达性、A* 寻路和实际移动阶段使用该网格。
- 该网格只把“允许的不可通过水地形”视为可走，不放开墙、山体、门、建筑等普通阻挡物。

#### Def 设计

新增文件建议放在：

`../../Defs/PathGridDefs/PathGrids_ArtificialMaid.xml`

内容示意：

```xml
<?xml version="1.0" encoding="utf-8"?>
<Defs>
  <PathGridDef>
    <defName>ArtificialMaidPathGrid</defName>
    <workerType>OuterrealmTechRobot.ArtificialMaidPathGrid</workerType>
    <fencePassable>true</fencePassable>
    <flying>false</flying>
  </PathGridDef>
</Defs>
```

不使用 `flying=true`，因为这里不是原版飞行。是否允许穿过围栏可以后续单独决定；如果只想改水，不想改围栏，应保留原版 fence 行为，或者再加一个 `ArtificialMaidFenceBlockedPathGrid`。

#### ArtificialMaidPathGrid 设计

新增类建议放在：

`Source/OuterrealmTechRobot/ArtificialMaidPathGrid.cs`

行为：

- 对普通可通行地形，直接调用 `base.CalculatedCostAt(...)`，保留原版火、雪、沙、Thing pathCost、门等逻辑。
- 对 `terrain.passability == Impassable` 且 `terrain.IsWater == true` 或 `terrain.tags` 包含 `Water` 的地形，进入自定义分支。
- 自定义分支返回一个 `< 10000` 的成本，例如：
  - 普通深水：`Mathf.Min(terrain.pathCost, 300)` 或固定 `30/42/60`
  - 毒深水：可以保留更高成本 `400`，除非希望女仆完全无视
- 自定义分支仍然检查 `thingGrid.ThingsListAt(c)`：
  - 如果有不可通过建筑/物品，返回 `10000`。
  - 这样女仆不会因为能走深海而顺便穿墙。
- 不在频繁调用中分配集合；直接 for 循环遍历 `List<Thing>` 和 `terrain.tags`。

建议把“可走深水”的判断写成无分配静态方法：

```csharp
public static bool CanArtificialMaidTraverseTerrain(TerrainDef terrain)
{
    if (terrain == null) return false;
    if (terrain.passability != Traversability.Impassable) return true;
    if (terrain.IsWater) return true;
    List<string> tags = terrain.tags;
    if (tags == null) return false;
    for (int i = 0; i < tags.Count; i++)
    {
        if (tags[i] == "Water") return true;
    }
    return false;
}
```

#### Harmony 接入点

需要补丁覆盖以下点：

1. `Pawn.GetPathContext(Pathing pathing)` 或 `Pathing.For(Pawn pawn)`
   - 当 `pawn.def == ArtificialMaidDefOf.ArtificialMaid` 时返回 `pathing.Get(ArtificialMaidPathGrid)`。
   - 作用：让 `WalkableBy(map, pawn)` 和移动阶段 `SetupMoveIntoNextCell()` 允许进入深水。

2. `Pathing.For(TraverseParms parms)`
   - 当 `parms.pawn` 是 `ArtificialMaid` 时返回 `pathing.Get(ArtificialMaidPathGrid)`。
   - 作用：让 `Reachability.CanReach(...)` 的 region/cell 可达性检查使用专用网格。

3. `PathFinderMapData.ParameterizeGridJob(...)`
   - Postfix 或 Transpiler：当 `request.pawn` 是 `ArtificialMaid` 时，将 `job.pathGridDirect` 改为女仆专用 `CostSource.Data`。
   - 作用：让真正的 A* `PathGridJob` 看到深水格成本 `< 10000`。
   - 仅 patch `Pathing.For(...)` 不够，因为原版这里硬编码 normal/fence cost source。
   - 注意：RimWorld 1.6 的 `PathGridJob` 是并行 Job，不建议直接把 `job.pathGridDirect` 指向 live `ArtificialMaidPathGrid.Grid_Unsafe`；应使用注册到 `PathFinderMapData` 的 `CostSource` 快照，原因见“RimWorld 1.6 并行寻路验证”。

4. `Pawn_PathFollower.StartPath(...)`
   - 需要处理内部硬编码的 `TraverseParms.For(TraverseMode.PassDoors)` 预检查。
   - 推荐 Transpiler 把这个调用替换成 helper：
     - 普通 Pawn：保持 `TraverseParms.For(TraverseMode.PassDoors)`。
     - `ArtificialMaid`：使用带 pawn 的 `TraverseParms.For(pawn, mode: TraverseMode.PassDoors)`，让 `Pathing.For(TraverseParms)` 补丁能命中。
   - 如果不处理这个点，目标区域被深海隔开时，女仆可能在正式寻路前就 `PatherFailed()`。

5. 现有 `Patch_Pawn_PathFollower_CostToMoveIntoCell`
   - 可以保留，让女仆移动耗时不受地形影响。
   - 但建议把它与新 `ArtificialMaidPathGrid` 的水格成本设定对齐，避免寻路认为水很贵而实际走起来完全无成本，导致路径选择不符合预期。

6. `PathFinder.MapGridRequest.For(PathRequest request)`
   - RimWorld 1.6 会用 `MapGridRequest` 缓存 `PathGridJob` 输出。
   - `MapGridRequest` 不包含 pawn 引用，只包含 `traverseParams` 的非 pawn 字段、`tuning`、`customizer`、`allowedArea`、`avoidGrid`。
   - 因此女仆请求必须有一个与普通 Pawn 不同的 key。推荐在 Postfix 中，当 `request.pawn` 是 `ArtificialMaid` 时，把 `__result.customizer` 设为一个单例 marker customizer。
   - 这个 marker customizer 只用于区分缓存 key，可以返回空 offset grid，不要分配新数组。

7. `PathFinderJob.connectivity`
   - RimWorld 1.6 的 A* 不直接枚举八邻格，而是读取 `PathFinderJob.connectivity`。
   - 原版 `ConnectivitySource.ComputeCellConnectivity(...)` 使用 `WalkableByAny()`，只看 `Normal` / `FenceBlocked`，不会看 `ArtificialMaidPathGrid`。
   - 因此需要一个女仆专用 `ConnectivitySource`，或者在 path job 参数化后为女仆替换 `job.connectivity`。
   - 推荐新增 `ArtificialMaidConnectivitySource : SimplePathFinderDataSource<CellConnection>`，注册到 `PathFinderMapData`，并在女仆 path job 中使用它。

#### DefOf / 初始化

在 `ArtificialMaidDefOf` 中增加：

```csharp
public static PathGridDef ArtificialMaidPathGrid;
```

静态构造里已有 `DefOfHelper.EnsureInitializedInCtor(typeof(ArtificialMaidDefOf));`，可继续沿用。

如果担心加载顺序或其他 Mod 移除 Def，所有调用 `pathing.Get(ArtificialMaidDefOf.ArtificialMaidPathGrid)` 前都应做 null fallback 到原版结果。

## RimWorld 1.6 并行寻路验证

用户提醒后再次用 rimsage 验证了 RimWorld 1.6 的寻路实现。结论是：方案 C 的“专用网格”方向仍然正确，但原先只靠替换 `Pathing.For(...)` 和 `PathFinderMapData.ParameterizeGridJob(...)` 的设计不完整，必须适配 1.6 的 Job 化和缓存机制。

### 1.6 的实际寻路流水线

1. `PathFinder.PathFinderTick()`
   - 每 tick 先 `ForceCompleteScheduledJobs()`，回收上一批 job。
   - 从 `workQueue` 取出本 tick 要算的 `PathRequest`。
   - `PathFinderMapData.GatherData(tmpCurrentWork)` 更新各类数据源。
   - `ScheduleGridJobs()` 先调度一个或多个 `PathGridJob : IJobParallelFor`。
   - `ScheduleBatchedPathJobs(...)` 再调度多个 `PathFinderJob : IJob`。

2. `PathGridJob`
   - 并行遍历整张地图所有格子，生成本次请求可用的 `grid`。
   - 输入包括 `pathGridDirect`、water、fence、building、danger、allowed area、avoid grid、customizer 等。
   - `CellIsPassable(index)` 的核心条件仍然是 `pathGridDirect[index] < 10000`。

3. `PathFinderJob`
   - 真正执行 A*。
   - 不直接遍历 `GenAdj`，而是读取 `connectivity[element]` 决定能扩展到哪些邻格。
   - 目标格成本来自 `grid[index]`，即上一步 `PathGridJob` 的输出。

4. `MapGridRequest`
   - `PathFinder` 用它缓存 `PathGridJob` 输出。
   - key 不包含 pawn 引用，只包含 `TraverseMode`、fence/danger/fog flags、buildable rect、`PathFinderCostTuning`、`customizer`、allowed area、avoid grid。

### 对原方案 C 的验证结果

验证结果如下：

- `ArtificialMaidPathGrid` 必要，但不充分。
- Patch `Pathing.For(Pawn)` / `Pathing.For(TraverseParms)` 必要，但不充分。
- Patch `PathFinderMapData.ParameterizeGridJob(...)` 必要，但不能直接读取 live `PathGrid.Grid_Unsafe`。
- 必须处理 `PathFinderJob.connectivity`，否则 A* 可能完全不会扩展进深水格。
- 必须处理 `MapGridRequest` key，否则女仆和普通 Pawn 可能复用彼此的 grid job 输出。
- 必须处理 `Reachability`，因为原版 region-based reachability 依赖 region/district；深水原本没有普通可走 region，光有女仆专用 `PathGrid` 不代表原版区域可达性会自动跨过深水。

### 为什么不能直接使用 live PathGrid.Grid_Unsafe

原版 `PathFinderMapData` 没有把 `PathGrid.Grid_Unsafe` 直接交给 job，而是通过 `CostSource` 复制：

- `CostSource.ComputeAll(...)` 把 `PathingContext.pathGrid.Grid_Unsafe` 拷贝到自己的 `NativeArray<int>`。
- `CostSource.UpdateIncrementally(...)` 只复制 dirty cells。
- `PathFinderMapData.ParameterizeGridJob(...)` 把 `normalCost.Data` 或 `fenceBlockedCost.Data` 传给 `PathGridJob.pathGridDirect`。

这在 1.6 并行寻路中很重要。`PathGridJob` 会被调度到 Job System 中异步读取输入数组；如果直接指向 live `ArtificialMaidPathGrid.Grid_Unsafe`，主线程后续地形/建筑/path cost dirty 更新可能与 job 读取同一个 `NativeArray`，存在数据竞争或 Unity NativeArray safety 风险。

因此修正建议是：

- 在 `PathFinderMapData` 构造后，为每张地图创建 `CostSource(map, map.pathing.Get(ArtificialMaidPathGrid))`。
- 用 `PathFinderMapData.RegisterSource(...)` 注册该 source，让它参与 `GatherData()` 的 full recompute 和 incremental update。
- 用 `ConditionalWeakTable<PathFinderMapData, ArtificialMaidPathFinderData>` 或类似结构保存女仆 source 引用。
- 在 `ParameterizeGridJob(...)` 中，女仆请求使用 `maidCostSource.Data`，而不是 live `PathGrid.Grid_Unsafe`。

### 为什么必须处理 connectivity

`PathFinderJob.Execute()` 扩展邻格时读取：

```csharp
CellConnection connections = this.connectivity[element];
```

而原版 `ConnectivitySource.ComputeCellConnectivity(...)` 的判断是：

```csharp
else if (!c.WalkableByAny(this.map))
    continue;
```

`WalkableByAny()` 只检查 `Normal` 和 `FenceBlocked`：

```csharp
return map.pathing.Normal.pathGrid.Walkable(c)
    || map.pathing.FenceBlocked.pathGrid.Walkable(c);
```

深海水在 Normal/FenceBlocked 下仍然是 `10000`，所以原版 connectivity 不会把深水邻格标为可连接。即使女仆专用 `PathGridJob.grid[index]` 把深水成本变成 `< 10000`，A* 也可能因为 connectivity 没有边而进不去。

修正建议：

- 新增 `ArtificialMaidConnectivitySource : SimplePathFinderDataSource<CellConnection>`。
- 计算规则与原版类似，但邻格可走条件改为：
  - 原版 `WalkableByAny(map)` 为真；或
  - `ArtificialMaidPathGrid.Walkable(c)` 为真。
- 仍然保留不可通过建筑、不可摧毁阻挡、地图边界、斜向阻挡规则。
- 在女仆 path job 参数化之后，把 `job.connectivity` 替换为 `maidConnectivitySource.Data`。

推荐接入方式：

- 对 `PathFinder.ScheduleBatchedPathJobs(...)` 和 `FindPathNow(...)` 做 Transpiler，在 `mapData.ParameterizePathJob(ref job)` 后插入：

```csharp
ArtificialMaidPathingUtility.ApplyMaidPathJobData(request, ref job);
```

这个 helper 在 `request.pawn` 是女仆时替换 `job.connectivity`，普通请求不做任何事。

### 为什么必须区分 MapGridRequest key

`ScheduleGridJobs()` 会按 `MapGridRequest.For(request)` 去重：

```csharp
if (!this.gridJobLookup.ContainsKey(PathFinder.MapGridRequest.For(request)))
    handle = this.ScheduleGridJob(request, handle).handle;
```

`ScheduleBatchedPathJobs()` 再用同一个 key 取 grid：

```csharp
PathFinder.MapGridRequest gridRequest = PathFinder.MapGridRequest.For(request);
PathFinder.ScheduledGridJob scheduledGridJob = this.gridJobLookup[gridRequest];
```

如果女仆请求和普通 Pawn 请求的 key 相同：

- 先遇到普通 Pawn：女仆可能复用普通 grid，深水仍是 `10000`。
- 先遇到女仆：普通 Pawn 可能复用女仆 grid，普通 Pawn 可能错误认为深水可走。

修正建议：

- Patch `PathFinder.MapGridRequest.For(PathRequest request)`。
- 当 `request.pawn.def == ArtificialMaidDefOf.ArtificialMaid` 时，把返回值里的 `customizer` 改成一个单例 marker。
- marker 只用于 key 区分，返回空 `NativeArray<ushort>`，不要改变成本。
- 普通 Pawn 仍保持原 key。

这样女仆 grid job 与普通 grid job 会分开缓存，但多个女仆之间仍可共享同一个女仆 grid job。

### Reachability 也不能只靠 Pathing.For

`PathRequest.Validate()` 会先调用 `pawn.CanReach(...)`。原版 `Reachability.CanReach(...)` 主要依赖 region/district；而深水作为 `passability=Impassable` 的地形，通常不会形成普通可走 region。

即使 `Pathing.For(TraverseParms)` 返回女仆专用网格，原版 region-based reachability 仍可能因为没有深水 region 而返回不可达。

修正建议：

- 对 `Reachability.CanReach(IntVec3, LocalTargetInfo, PathEndMode, TraverseParms)` 增加女仆专用分支。
- 当 `traverseParams.pawn` 是女仆时，不走原版 region cache，改用基于女仆专用 path grid / connectivity 的 cell flood fill。
- 只验证“女仆是否能走到目标附近”，不要把结果写入原版 region cache，避免普通 Pawn 复用。
- 对普通 Pawn 完全不改变。

### 修正后的方案 C 定义

适配 RimWorld 1.6 后，方案 C 应定义为：

1. `ArtificialMaidPathGrid`
   - 负责把允许的深水地形变成 `< 10000`。

2. `ArtificialMaidCostSource`
   - 注册到 `PathFinderMapData`。
   - 给并行 `PathGridJob` 提供稳定快照，不直接暴露 live `PathGrid.Grid_Unsafe`。

3. `ArtificialMaidConnectivitySource`
   - 注册到 `PathFinderMapData`。
   - 给女仆 `PathFinderJob` 提供包含深水连接的邻接图。

4. `MapGridRequest` key marker
   - 区分女仆 grid job 和普通 Pawn grid job，避免缓存混用。

5. `Reachability` 女仆分支
   - 避免原版 region-based reachability 在深水处提前失败。

6. `Pawn_PathFollower` 移动阶段补丁
   - `Pathing.For(Pawn)` / `WalkableBy` 使用女仆专用 path grid。
   - `StartPath` 的 hardcoded `PassDoors` 预检查必须带 pawn 或绕到女仆 reachability 分支。

这个修正后的方案 C 才能完整适配 RimWorld 1.6 的并行寻路。

## 当前方案 C 需要的修改与 HarmonyPatch 可行性

结论：可以不修改原版 Assembly-CSharp，也不需要直接改原版源码；所有“接入原版运行流程”的部分都可以用 `HarmonyPatch` 完成。但这不等于“只写 HarmonyPatch 就够了”。方案 C 仍然需要新增本 Mod 自己的 Def、辅助类和数据源类：

- 新增 XML Def：`PathGridDef ArtificialMaidPathGrid`。
- 新增 C# 类：`ArtificialMaidPathGrid`。
- 新增 C# 类：女仆 pathfinder 数据持有结构，例如 `ArtificialMaidPathFinderData`。
- 新增 C# 类：`ArtificialMaidConnectivitySource`。
- 新增 C# helper：`ArtificialMaidPathingUtility`，集中做女仆判断、source 注册、job 参数替换、reachability flood fill。
- 新增 C# marker：用于区分 `MapGridRequest` key 的 `IPathGridCustomizer` 实现。

也就是说，推荐实现方式是“新增本 Mod 自己的类 + HarmonyPatch 挂入原版流程”，而不是直接改原版代码。

### 修改点清单

| 修改点 | 是否必须 | 推荐实现 | 能否 HarmonyPatch 完成 | 说明 |
| --- | --- | --- | --- | --- |
| 新增 `PathGridDef` | 必须 | XML Def | 不属于 Harmony | DefDatabase 需要在 `Pathing` 构造地图 path grids 前知道这个 Def。 |
| 新增 `ArtificialMaidPathGrid` | 必须 | 新 C# 类 | 不属于 Harmony | 由新增 `PathGridDef.workerType` 引用。 |
| `ArtificialMaidDefOf` 增加 `ArtificialMaidPathGrid` 字段 | 建议 | 直接改本 Mod 源码 | 不需要 Harmony | 这是本 Mod 自己的 DefOf，不是原版补丁。 |
| 给 `PathFinderMapData` 注册女仆数据源 | 必须 | Patch 构造函数 Postfix | 可以 | `PathFinderMapData(Map map)` 有 map 参数，可在 Postfix 创建 `CostSource` 和 `ArtificialMaidConnectivitySource`，调用 `RegisterSource(...)`。 |

| `PathFinderJob.connectivity` 替换为女仆连接图 | 必须 | Transpiler 或双 Postfix 传递上下文 | 可以，但比普通 Prefix/Postfix 复杂 | 原版 `PathFinderMapData.ParameterizePathJob(ref job)` 没有 `PathRequest` 参数，不能单独靠它判断 pawn。 |
| `Pathing.For(Pawn)` / `Pawn.GetPathContext(...)` | 必须 | Prefix/Postfix | 可以 | 让 `WalkableBy(map, pawn)` 和移动阶段使用女仆 `PathingContext`。 |

| 现有 `CostToMoveIntoCell` 补丁 | 已有 | 保留或调整 | 已是 HarmonyPatch | 只影响移动耗时，不影响可通行性。 |

### 可以完全用 HarmonyPatch 接入的部分

以下原版接入点都可以用 `HarmonyPatch` 完成：

1. `PathFinderMapData` 构造函数 Postfix
   - 创建女仆专用数据：
     - `CostSource maidCost = new CostSource(map, map.pathing.Get(ArtificialMaidPathGrid))`
     - `ArtificialMaidConnectivitySource maidConnectivity = new ArtificialMaidConnectivitySource(map)`
   - 调用 `__instance.RegisterSource(maidCost)` 和 `__instance.RegisterSource(maidConnectivity)`。
   - 把两者保存到 `ConditionalWeakTable<PathFinderMapData, ArtificialMaidPathFinderData>`。

2. `PathFinder.MapGridRequest.For(PathRequest request)` Postfix
   - 当 `request.pawn` 是女仆时修改 `__result.customizer`。
   - 注意不要简单覆盖所有 customizer，否则会丢失原 customizer 的缓存区分。
   - 推荐：
     - `request.customizer == null`：使用一个静态单例 marker。
     - `request.customizer != null`：使用包装 key，例如 `ArtificialMaidGridKeyCustomizer(originalCustomizer)`，其 `Equals/GetHashCode` 包含原 customizer。
   - 这个 marker 只用于 `MapGridRequest` equality。原版 `ParameterizeGridJob(...)` 实际读取的是 `request.customizer`，不是 `query.customizer`，所以 marker 不会改变真实 path cost。

3. `PathFinderMapData.ParameterizeGridJob(...)` Postfix
   - 参数里有 `PathRequest request` 和 `ref PathGridJob job`。
   - 如果是女仆请求：
     - `job.pathGridDirect = maidCostSource.Data`
   - 其他字段仍用原版已经填好的 water/fence/building/danger/area/avoid grid。

4. `Pathing.For(Pawn)` 或 `Pawn.GetPathContext(...)` Prefix/Postfix
   - 最简单是 patch `Pawn.GetPathContext(Pathing pathing)`：
     - 女仆返回 `pathing.Get(ArtificialMaidPathGrid)`。
     - 普通 Pawn 不变。
   - 如果想保留 fence-blocked 语义，可再做一个女仆 fence-blocked 网格；当前方案为了深水通行，先返回单一女仆网格。

5. `Pathing.For(TraverseParms)` Prefix/Postfix
   - 当 `parms.pawn` 是女仆时返回 `Get(ArtificialMaidPathGrid)`。
   - 这个点影响 `Reachability`、`TouchPathEndModeUtility`、`PathFinder.MakeDestination(...)`。

6. `Reachability.CanReach(IntVec3, LocalTargetInfo, PathEndMode, TraverseParms)` Prefix
   - 当 `traverseParams.pawn` 是女仆时：
     - 用女仆 `PathGrid` / `ArtificialMaidConnectivitySource` 做 cell flood fill。
     - 找到能 `ReachabilityImmediate.CanReachImmediate(...)` 目标的位置后，设置 `__result = true`，`return false`。
     - 找不到则 `__result = false`，`return false`。
   - 普通 Pawn `return true` 走原版。
   - 不要写入原版 `ReachabilityCache`，避免普通 Pawn 复用女仆结果。

### 需要 Transpiler 或上下文传递的部分

有两个点只靠简单 Prefix/Postfix 不够稳。

#### 1. 替换 `PathFinderJob.connectivity`

原版调用顺序是：

```csharp
this.ParameterizePathJob(..., request);
this.mapData.ParameterizePathJob(ref job);
job.Schedule(...);
```

`PathFinder.ParameterizePathJob(...)` 有 `PathRequest request`，但它执行后，`PathFinderMapData.ParameterizePathJob(ref job)` 会继续把 `job.connectivity` 覆盖成原版 connectivity。

`PathFinderMapData.ParameterizePathJob(ref job)` 有 `ref PathFinderJob job`，但没有 `PathRequest request`，所以它自己无法判断当前是不是女仆请求。

推荐两种实现：

1. Transpiler call-site 注入，最稳：
   - Patch `PathFinder.ScheduleBatchedPathJobs(...)`。
   - Patch `PathFinder.FindPathNow(...)`。
   - 在 `this.mapData.ParameterizePathJob(ref job)` 后插入：

```csharp
ArtificialMaidPathingUtility.ApplyMaidPathJobData(request, ref job);
```

2. 上下文传递，少写 IL 但更脆：
   - Patch 私有 `PathFinder.ParameterizePathJob(...)` Postfix，记录当前 `PathRequest` 到 `[ThreadStatic]` 字段。
   - Patch `PathFinderMapData.ParameterizePathJob(ref job)` Postfix，读取并清理该字段，再替换 `job.connectivity`。
   - 由于 1.6 的 job 参数化仍在主线程执行，这通常可行；但如果其他 Mod 改写调用顺序，风险高于 Transpiler。

建议用 Transpiler。它仍然是 `HarmonyPatch`。

#### 2. 修正 `Pawn_PathFollower.StartPath(...)`

原版 `StartPath(...)` 内部有硬编码：

```csharp
this.pawn.Map.reachability.CanReach(
    this.pawn.Position,
    dest,
    peMode,
    TraverseParms.For(TraverseMode.PassDoors))
```

这个 `TraverseParms` 没有 pawn，因此 `Reachability` 的女仆 Prefix 无法知道这是女仆请求。

推荐用 Transpiler 把这个构造替换为 helper：

```csharp
ArtificialMaidPathingUtility.PassDoorsTraverseParmsFor(this.pawn)
```

helper 行为：

- 普通 Pawn：返回 `TraverseParms.For(TraverseMode.PassDoors)`。
- 女仆：返回 `TraverseParms.For(pawn, mode: TraverseMode.PassDoors)`。

这样 `Reachability.CanReach(...)` 能拿到 `traverseParams.pawn`，并进入女仆分支。

也可以用 Prefix 完整重写 `StartPath(...)` 的女仆分支，但这个方法内部状态较多，涉及 `destination`、`peMode`、`curPathRequest`、移动重置、占位 reservation、到达/失败处理；复制原版逻辑更容易在 1.6 后续小版本中坏掉。因此不推荐 Prefix 重写。

### 不建议用 HarmonyPatch 解决的部分

以下内容虽然理论上也能用 Harmony 反射强行做，但不推荐：

1. 不建议运行时修改原版 `TerrainDef.passability`
   - 这会全局影响所有 Pawn。
   - 也会影响 region、建筑、地图生成、敌袭、动物等系统。

2. 不建议用 Harmony 修改 `PathGridJob.Execute(...)`
   - 它是 `[BurstCompile]` 的 `IJobParallelFor`。
   - Burst job 的方法不适合作为业务 Mod 的稳定 patch 点。
   - 应在 job 参数化前提供正确的 `pathGridDirect`、`connectivity` 和 key，而不是改 job 内部算法。

3. 不建议用全局静态“当前 Pawn”影响 `PathGrid` 或 `Reachability`
   - 1.6 寻路会并行调度 job。
   - 静态当前 pawn 容易在多个请求之间串扰。
   - 正确做法是让 request grid key、cost source、connectivity source 都显式区分女仆。

### 是否可以全部使用 HarmonyPatch 完成

如果“全部”指的是对原版流程的接入：可以，全部可以用 `HarmonyPatch` 完成。

需要的 Harmony 类型大致是：

- Prefix/Postfix：
  - `PathFinderMapData` 构造函数
  - `PathFinderMapData.ParameterizeGridJob(...)`
  - `PathFinder.MapGridRequest.For(...)`
  - `Pathing.For(Pawn)` / `Pawn.GetPathContext(...)`
  - `Pathing.For(TraverseParms)`
  - `Reachability.CanReach(...)`

- Transpiler：
  - `PathFinder.ScheduleBatchedPathJobs(...)`
  - `PathFinder.FindPathNow(...)`
  - `Pawn_PathFollower.StartPath(...)`

- 可选 Prefix/Postfix 替代 Transpiler：
  - 用 `[ThreadStatic]` 上下文桥接 `PathFinder.ParameterizePathJob(...)` 和 `PathFinderMapData.ParameterizePathJob(...)`，但不如 call-site Transpiler 稳。

如果“全部”指的是不新增任何类、不新增任何 Def，只写 patch 方法：不可以。因为至少需要：

- `ArtificialMaidPathGrid` 作为 `PathGridDef.workerType`。
- `ArtificialMaidConnectivitySource` 作为并行 A* 的连接图数据源。
- marker customizer 作为 `MapGridRequest` key。
- 数据持有结构保存每个 `PathFinderMapData` 对应的女仆 source。

最终判断：方案 C 可以通过“新增本 Mod 类型 + HarmonyPatch 原版接入点”的方式完整实现，无需改原版源码。但实现复杂度较高，关键风险集中在两个 Transpiler：`PathFinder` 的 path job 参数注入，以及 `Pawn_PathFollower.StartPath` 的 hardcoded `PassDoors` 替换。

## Transpiler 编写方法与关键代码

这里给出方案 C 中两个必须 Transpiler 的写法。目标不是手写完整 IL，而是用 Harmony 的 `CodeInstruction` 对原版 IL 做“小范围替换/插入”。

当前项目引用的是 `Lib.Harmony 2.4.2`，可以使用：

- `HarmonyLib.CodeInstruction`
- `CodeInstruction.Calls(...)`
- `AccessTools.Method(...)`
- `AccessTools.Field(...)`

### 编写 Transpiler 的原则

1. 不硬编码 IL local index
   - C# 编译器可能改变局部变量编号。
   - 推荐通过 `MethodBase.GetMethodBody().LocalVariables` 按类型查找 `PathRequest` 和 `PathFinderJob` 的 local index。

2. 只匹配非常稳定的调用点
   - `PathFinderMapData.ParameterizePathJob(ref PathFinderJob job)` 是明确调用点。
   - `TraverseParms.For(TraverseMode, Danger, bool, bool, bool, bool, bool)` 是明确调用点。

3. 保留 labels
   - 被替换 IL 的第一条指令可能有跳转 label。
   - 替换时要把 label 移到新插入的第一条指令上。

4. 匹配失败时不要静默成功
   - 至少 `Log.Error`。
   - 开发阶段可以直接抛异常，正式版本建议 log 后返回原 IL，避免整个游戏启动失败。

### 需要的 helper

Transpiler 插入的代码应尽量调用普通 C# helper，把复杂逻辑放在 helper 里，不要塞进 IL。

```csharp
using Verse;
using Verse.AI;

namespace OuterrealmTechRobot
{
    public static class ArtificialMaidPathingUtility
    {
        public static bool IsArtificialMaid(Pawn pawn)
        {
            return pawn != null && pawn.def == ArtificialMaidDefOf.ArtificialMaid;
        }

        public static void ApplyMaidPathJobData(PathRequest request, ref PathFinderJob job)
        {
            if (request == null || !IsArtificialMaid(request.pawn))
            {
                return;
            }

            if (!ArtificialMaidPathFinderData.TryGet(request.map.pathFinder.MapData, out ArtificialMaidPathFinderData data))
            {
                return;
            }

            job.connectivity = data.MaidConnectivity.Data;
        }

        public static TraverseParms PassDoorsTraverseParmsFor(Pawn pawn)
        {
            if (IsArtificialMaid(pawn))
            {
                return TraverseParms.For(pawn, mode: TraverseMode.PassDoors);
            }

            return TraverseParms.For(TraverseMode.PassDoors);
        }
    }
}
```

这里假设 `ArtificialMaidPathFinderData.TryGet(...)` 能通过 `PathFinderMapData` 找到注册过的女仆数据源。`MaidConnectivity.Data` 的类型应是 `NativeArray<CellConnection>.ReadOnly`，与 `PathFinderJob.connectivity` 字段一致。

### 通用 IL 工具函数

这几个函数用于生成 `ldloc`、`ldloca`，并按类型查找本地变量。

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Reflection;
using System.Reflection.Emit;
using HarmonyLib;
using Verse;

namespace OuterrealmTechRobot
{
    internal static class ArtificialMaidTranspilerUtility
    {
        public static int FindSingleLocal(MethodBase method, Type localType)
        {
            List<int> matches = method.GetMethodBody()
                .LocalVariables
                .Where(l => l.LocalType == localType)
                .Select(l => l.LocalIndex)
                .ToList();

            if (matches.Count != 1)
            {
                throw new InvalidOperationException(
                    $"{method.DeclaringType?.FullName}.{method.Name}: expected exactly one local of type {localType.FullName}, found {matches.Count}.");
            }

            return matches[0];
        }

        public static CodeInstruction Ldloc(int index)
        {
            switch (index)
            {
                case 0: return new CodeInstruction(OpCodes.Ldloc_0);
                case 1: return new CodeInstruction(OpCodes.Ldloc_1);
                case 2: return new CodeInstruction(OpCodes.Ldloc_2);
                case 3: return new CodeInstruction(OpCodes.Ldloc_3);
                default:
                    return new CodeInstruction(index <= byte.MaxValue ? OpCodes.Ldloc_S : OpCodes.Ldloc, index);
            }
        }

        public static CodeInstruction Ldloca(int index)
        {
            return new CodeInstruction(index <= byte.MaxValue ? OpCodes.Ldloca_S : OpCodes.Ldloca, index);
        }

        public static bool IsLdcI4(CodeInstruction instruction, int value)
        {
            if (instruction.opcode == OpCodes.Ldc_I4_M1) return value == -1;
            if (instruction.opcode == OpCodes.Ldc_I4_0) return value == 0;
            if (instruction.opcode == OpCodes.Ldc_I4_1) return value == 1;
            if (instruction.opcode == OpCodes.Ldc_I4_2) return value == 2;
            if (instruction.opcode == OpCodes.Ldc_I4_3) return value == 3;
            if (instruction.opcode == OpCodes.Ldc_I4_4) return value == 4;
            if (instruction.opcode == OpCodes.Ldc_I4_5) return value == 5;
            if (instruction.opcode == OpCodes.Ldc_I4_6) return value == 6;
            if (instruction.opcode == OpCodes.Ldc_I4_7) return value == 7;
            if (instruction.opcode == OpCodes.Ldc_I4_8) return value == 8;
            if (instruction.opcode == OpCodes.Ldc_I4_S) return Convert.ToInt32(instruction.operand) == value;
            if (instruction.opcode == OpCodes.Ldc_I4) return Convert.ToInt32(instruction.operand) == value;
            return false;
        }

        public static void MoveLabels(CodeInstruction from, CodeInstruction to)
        {
            if (from.labels.Count == 0)
            {
                return;
            }

            to.labels.AddRange(from.labels);
            from.labels.Clear();
        }
    }
}
```

如果 `Ldloc_S` / `Ldloca_S` 的 operand 在实际编译环境中要求 `byte` 而不是 `int`，把 `index` 改成 `(byte)index` 即可。Harmony 通常能接受 local index。

### Transpiler 1：给 PathFinderJob 注入女仆 connectivity

目标源码位置有两个：

`PathFinder.ScheduleBatchedPathJobs(...)`

```csharp
this.ParameterizePathJob(..., request);
this.mapData.ParameterizePathJob(ref job);
dependsOn1 = job.Schedule<PathFinderJob>(dependsOn2);
```

`PathFinder.FindPathNow(...)`

```csharp
this.ParameterizePathJob(..., request);
this.mapData.ParameterizePathJob(ref job);
job.Run<PathFinderJob>();
```

需要在 `this.mapData.ParameterizePathJob(ref job)` 后插入：

```csharp
ArtificialMaidPathingUtility.ApplyMaidPathJobData(request, ref job);
```

关键 Transpiler：

```csharp
using System;
using System.Collections.Generic;
using System.Reflection;
using System.Reflection.Emit;
using HarmonyLib;
using Verse;

namespace OuterrealmTechRobot
{
    [HarmonyPatch(typeof(PathFinder), "ScheduleBatchedPathJobs")]
    public static class Patch_PathFinder_ScheduleBatchedPathJobs_Transpiler
    {
        public static IEnumerable<CodeInstruction> Transpiler(IEnumerable<CodeInstruction> instructions, MethodBase original)
        {
            return InsertApplyMaidPathJobData(instructions, original);
        }
    }

    [HarmonyPatch(typeof(PathFinder), nameof(PathFinder.FindPathNow),
        new Type[]
        {
            typeof(IntVec3),
            typeof(LocalTargetInfo),
            typeof(TraverseParms),
            typeof(Nullable<PathFinderCostTuning>),
            typeof(PathEndMode),
            typeof(PathRequest.IPathGridCustomizer)
        })]
    public static class Patch_PathFinder_FindPathNow_Transpiler
    {
        public static IEnumerable<CodeInstruction> Transpiler(IEnumerable<CodeInstruction> instructions, MethodBase original)
        {
            return InsertApplyMaidPathJobData(instructions, original);
        }
    }

    internal static partial class ArtificialMaidPathFinderTranspilers
    {
        private static IEnumerable<CodeInstruction> InsertApplyMaidPathJobData(
            IEnumerable<CodeInstruction> instructions,
            MethodBase original)
        {
            List<CodeInstruction> codes = new List<CodeInstruction>(instructions);

            int requestLocal = ArtificialMaidTranspilerUtility.FindSingleLocal(original, typeof(PathRequest));
            int jobLocal = ArtificialMaidTranspilerUtility.FindSingleLocal(original, typeof(PathFinderJob));

            MethodInfo parameterizePathJob = AccessTools.Method(
                typeof(PathFinderMapData),
                nameof(PathFinderMapData.ParameterizePathJob),
                new Type[] { typeof(PathFinderJob).MakeByRefType() });

            MethodInfo applyMaidPathJobData = AccessTools.Method(
                typeof(ArtificialMaidPathingUtility),
                nameof(ArtificialMaidPathingUtility.ApplyMaidPathJobData));

            int insertions = 0;

            for (int i = 0; i < codes.Count; i++)
            {
                if (!codes[i].Calls(parameterizePathJob))
                {
                    continue;
                }

                codes.InsertRange(i + 1, new[]
                {
                    ArtificialMaidTranspilerUtility.Ldloc(requestLocal),
                    ArtificialMaidTranspilerUtility.Ldloca(jobLocal),
                    new CodeInstruction(OpCodes.Call, applyMaidPathJobData)
                });

                insertions++;
                i += 3;
            }

            if (insertions != 1)
            {
                Log.Error(
                    $"ArtificialMaid: expected one PathFinderMapData.ParameterizePathJob call in {original.DeclaringType?.FullName}.{original.Name}, found {insertions}.");
            }

            return codes;
        }
    }
}
```

为什么用 local type 找变量：

- `ScheduleBatchedPathJobs(...)` 和 `FindPathNow(...)` 各自都有一个 `PathRequest request` local。
- 两个方法也各自都有一个 `PathFinderJob job` local。
- 通过类型找 local，比硬编码 `ldloc.s 8` 之类的编号稳定。

这个 Transpiler 的效果等价于把原版改成：

```csharp
this.mapData.ParameterizePathJob(ref job);
ArtificialMaidPathingUtility.ApplyMaidPathJobData(request, ref job);
```

普通 Pawn 的 `ApplyMaidPathJobData` 会立即返回，不改变行为。

### Transpiler 2：替换 Pawn_PathFollower.StartPath 的 PassDoors

目标源码：

```csharp
if (!this.pawn.Map.reachability.CanReach(
        this.pawn.Position,
        dest,
        peMode,
        TraverseParms.For(TraverseMode.PassDoors)))
{
    this.PatherFailed();
}
```

问题是 `TraverseParms.For(TraverseMode.PassDoors)` 没有 pawn。女仆专用 `Reachability` Prefix 无法识别这是女仆请求。

要替换成：

```csharp
ArtificialMaidPathingUtility.PassDoorsTraverseParmsFor(this.pawn)
```

关键 Transpiler：

```csharp
using System;
using System.Collections.Generic;
using System.Reflection;
using System.Reflection.Emit;
using HarmonyLib;
using Verse;
using Verse.AI;

namespace OuterrealmTechRobot
{
    [HarmonyPatch(typeof(Pawn_PathFollower), nameof(Pawn_PathFollower.StartPath))]
    public static class Patch_Pawn_PathFollower_StartPath_Transpiler
    {
        public static IEnumerable<CodeInstruction> Transpiler(IEnumerable<CodeInstruction> instructions)
        {
            List<CodeInstruction> codes = new List<CodeInstruction>(instructions);

            MethodInfo traverseForMode = AccessTools.Method(
                typeof(TraverseParms),
                nameof(TraverseParms.For),
                new Type[]
                {
                    typeof(TraverseMode),
                    typeof(Danger),
                    typeof(bool),
                    typeof(bool),
                    typeof(bool),
                    typeof(bool),
                    typeof(bool)
                });

            FieldInfo pawnField = AccessTools.Field(typeof(Pawn_PathFollower), "pawn");

            MethodInfo helper = AccessTools.Method(
                typeof(ArtificialMaidPathingUtility),
                nameof(ArtificialMaidPathingUtility.PassDoorsTraverseParmsFor));

            int replacements = 0;

            for (int i = 0; i < codes.Count; i++)
            {
                if (!codes[i].Calls(traverseForMode))
                {
                    continue;
                }

                // TraverseParms.For(TraverseMode.PassDoors) with optional arguments compiles as:
                // mode=PassDoors(1), maxDanger=Deadly(3), canBashDoors=false,
                // alwaysUseAvoidGrid=false, canBashFences=false,
                // avoidPersistentDanger=true, fogBlocked=false, call For(...)
                int start = i - 7;
                if (start < 0 ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 0], (int)TraverseMode.PassDoors) ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 1], (int)Danger.Deadly) ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 2], 0) ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 3], 0) ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 4], 0) ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 5], 1) ||
                    !ArtificialMaidTranspilerUtility.IsLdcI4(codes[start + 6], 0))
                {
                    Log.Error("ArtificialMaid: found TraverseParms.For in Pawn_PathFollower.StartPath, but argument pattern did not match PassDoors defaults.");
                    continue;
                }

                CodeInstruction loadThis = new CodeInstruction(OpCodes.Ldarg_0);
                ArtificialMaidTranspilerUtility.MoveLabels(codes[start], loadThis);

                codes.RemoveRange(start, 8);
                codes.InsertRange(start, new[]
                {
                    loadThis,
                    new CodeInstruction(OpCodes.Ldfld, pawnField),
                    new CodeInstruction(OpCodes.Call, helper)
                });

                replacements++;
                i = start + 2;
            }

            if (replacements != 1)
            {
                Log.Error($"ArtificialMaid: expected one TraverseParms.For(PassDoors) replacement in Pawn_PathFollower.StartPath, replaced {replacements}.");
            }

            return codes;
        }
    }
}
```

这个 Transpiler 的效果等价于把原版改成：

```csharp
TraverseParms parms = ArtificialMaidPathingUtility.PassDoorsTraverseParmsFor(this.pawn);
if (!this.pawn.Map.reachability.CanReach(this.pawn.Position, dest, peMode, parms))
{
    this.PatherFailed();
}
```

普通 Pawn 仍返回原版 `TraverseParms.For(TraverseMode.PassDoors)`，所以普通逻辑不变。女仆会返回带 pawn 的 `TraverseParms.For(pawn, mode: TraverseMode.PassDoors)`，从而让 `Reachability.CanReach(...)` 的女仆 Prefix 能识别请求。

### 编写时如何验证 Transpiler 是否命中

推荐验证步骤：

1. 在每个 Transpiler 中统计 `insertions` / `replacements`。
2. 不是 `1` 时输出 `Log.Error`。
3. 开发阶段打开 Harmony debug：

```csharp
Harmony.DEBUG = true;
```

4. 启动游戏后检查 Player.log，确认 patch 没有报错。
5. 在开发地图上测试女仆跨深海寻路。

如果想从 IL 层确认原版调用点，可以用 IL 工具查看 `Assembly-CSharp.dll`。例如用 `ildasm` 导出对应方法，重点找：

```il
callvirt instance void Verse.PathFinderMapData::ParameterizePathJob(valuetype Verse.PathFinderJob&)
call valuetype Verse.TraverseParms Verse.TraverseParms::For(...)
```

也可以用 ILSpy/dnSpy 查看 C# 反编译，通常比直接读 IL 更直观。实际写 Harmony Transpiler 时，以 `AccessTools.Method(...)` 匹配方法调用，比按裸 IL 文本匹配更稳。

### 常见错误

1. 忘记 patch `FindPathNow(...)`
   - `PathFinderTick()` 的队列寻路会走 `ScheduleBatchedPathJobs(...)`。
   - 一些同步路径查询会走 `FindPathNow(...)`。
   - 两个都要插入 `ApplyMaidPathJobData(...)`。

2. 只 patch `PathFinderMapData.ParameterizePathJob(ref job)`
   - 这个方法没有 `PathRequest` 参数，无法知道当前 pawn。
   - 除非使用额外上下文，否则不够。

3. marker customizer 改了 `request.customizer`
   - 不建议直接改 `request.customizer`，因为原版 `ParameterizeGridJob(...)` 会读取它生成 `job.custom`。
   - 推荐只在 `MapGridRequest.For(...)` 的 Postfix 里改 `__result.customizer`，仅用于缓存 key。

4. 在 Transpiler 里大量写业务逻辑
   - Transpiler 只负责插入 helper call。
   - 真正逻辑放在普通 C# helper，便于调试和测试。

## 方案 C 的性能影响

### 固定内存成本

原版 `Pathing` 构造函数会遍历所有 `PathGridDef`，为每张地图创建一个对应的 `PathGrid`。`PathGrid` 内部持有一个 `NativeArray<int>`，长度等于地图格子数。

如果按 RimWorld 1.6 修正后的方案 C 实现，每张地图至少会新增：

- `ArtificialMaidPathGrid`：一个 `NativeArray<int>`。
- `ArtificialMaidCostSource`：一个 `NativeArray<int>`，作为并行 `PathGridJob` 的稳定快照。
- `ArtificialMaidConnectivitySource`：一个 `NativeArray<CellConnection>`，`CellConnection` 是 byte enum，约等于每格 1 byte。

估算内存：

- `250 x 250` 地图：约 `62,500 * 9 = 562 KB`
- `325 x 325` 地图：约 `105,625 * 9 = 950 KB`
- `400 x 400` 地图：约 `160,000 * 9 = 1.37 MB`

此外，原版在 `DisableIncrementalDirtying()` 时会为每个 `PathGrid` 创建一个 `NativeBitArray dirty`。这通常只在批量地形/建筑变化时临时存在，内存量远小于 `NativeArray<int>`。

结论：内存成本是稳定、可预估的，单地图通常在 0.5 到 1.5 MB 量级。多地图同时加载时按地图数量线性增加。

### 地图初始化与路径成本重算

原版 `Pathing.RecalculateAllPerceivedPathCosts()` 会遍历所有 `PathGrid`，每个网格都对全地图所有格子计算一次成本。新增一个 `PathGridDef` 后，相关全图重算会多一次全图遍历。

原版默认已有 `Normal`、`FenceBlocked`、`Flying` 三个网格。新增 `ArtificialMaidPathGrid` 后，PathGrid 层面的全图重算从 3 份变成 4 份，理论上这个子系统增加约 33% 的网格计算量。

另外，`PathFinderMapData.GatherData(...)` 会并行调用所有 `IPathFinderDataSource.ComputeAll/UpdateIncrementally`。注册 `ArtificialMaidCostSource` 和 `ArtificialMaidConnectivitySource` 后，full recompute 时还会多复制一份成本网格、重算一份连接图。

实际影响一般集中在：

- 地图生成/加载后的路径成本初始化。
- 大规模地形变化、批量建造/拆除、批量桥梁/地板变化。
- 调试或其他 Mod 主动触发全图 path cost 重算。

普通游戏 tick 中不会每 tick 全图重算，所以这不是持续性 tick 压力。

### 增量重算成本

原版 `Pathing.RecalculatePerceivedPathCostAt(IntVec3 c)` 会遍历所有 `PathGrid`，对单格重新计算。新增一个网格后，每个 dirty cell 会多一次 `ArtificialMaidPathGrid.CalculatedCostAt(...)`。

常见触发来源：

- 建筑生成/消失/血量变化。
- 地形变化。
- `PathCostRecalculate` 事件。

如果 `ArtificialMaidPathGrid` 的实现对普通地形直接走 `base.CalculatedCostAt(...)`，并且只在 `terrain.passability == Impassable` 时做少量水地形判断，则单格额外成本很低。需要避免在该方法中使用 LINQ、分配临时集合、频繁字符串构造或反射。

### 女仆寻路时的 A* 成本

`PathFinderMapData.ParameterizeGridJob(...)` 原版只把 `normalCost` 或 `fenceBlockedCost` 传给 `PathGridJob.pathGridDirect`。方案 C 需要在 `request.pawn` 是 `ArtificialMaid` 时替换成专用网格。

性能影响只应发生在女仆的 path request 上：

- 普通 Pawn 继续使用原版 `normalCost/fenceBlockedCost`。
- 女仆使用 `ArtificialMaidPathGrid`，A* 会把深水视为可通行。

这会带来一个重要变化：以前深海水是硬阻挡，A* 不会扩展这些格子；现在深海水可通行，女仆在海岸、岛屿、海冰、海洋地图上可能搜索更多格子。最坏情况下，如果目标很远且水域巨大，单次寻路会比原版更贵。

缓解建议：

- 深水 path cost 不要设得过低。建议保留较高成本，例如普通深水 `300`，毒深水 `400`，或者至少高于浅水。
- 如果希望女仆“可以走但不主动偏爱走”，保留原版水地形的高成本更合理。
- 不建议把深水成本设为 `1`，否则女仆可能倾向于横穿大片海洋，扩大寻路搜索范围，也会产生不符合直觉的路线。
- 只在 `request.pawn.def == ArtificialMaidDefOf.ArtificialMaid` 时替换网格，不要全局替换 `PathGridJob.pathGridDirect`。

### 可达性缓存影响

`Reachability.CanReach(...)` 会根据 `TraverseParms` 和区域结果做缓存。方案 C 需要让女仆可达性使用带 pawn 的 `TraverseParms`，避免把“女仆可达”的结果误共享给普通 Pawn。

注意点：

- `TraverseParms` 的相等与哈希包含 `pawn` 引用，因此使用 `TraverseParms.For(pawn, mode: ...)` 能避免普通 Pawn 复用女仆的可达性结果。
- `Pawn_PathFollower.StartPath(...)` 里的原版硬编码 `TraverseParms.For(TraverseMode.PassDoors)` 没有 pawn，必须替换，否则既不能命中女仆专用网格，也可能污染或误用普通可达性语义。
- 不要用“全局当前 pawn”这类静态变量临时影响 `Reachability`，那会带来缓存错配和线程/Job 调度风险。

### Harmony 补丁调用频率

建议补丁本身保持极轻：

- `Pathing.For(Pawn)` / `Pawn.GetPathContext(...)` 会被较频繁调用，判断应只是 `pawn != null && pawn.def == ArtificialMaidDefOf.ArtificialMaid`。
- `Pathing.For(TraverseParms)` 也会被可达性与寻路频繁调用，同样只做常量级判断。
- `PathFinderMapData.ParameterizeGridJob(...)` 只在生成寻路网格任务时调用，频率低于每 tick 移动。
- `Pawn_PathFollower.StartPath(...)` 只在开始路径时调用，不是每格移动都调用。

不要在这些补丁中：

- 搜索 DefDatabase。
- 使用反射。
- 创建新数组/列表。
- 用 LINQ 过滤地图对象。
- 每次调用写日志。

### 与 PathFinderMapData 的数据源关系

原版 `PathFinderMapData` 只创建了 `normalCost`、`fenceBlockedCost`、`flyingCost` 三个 `CostSource`。`CostSource` 本质是把某个 `PathingContext.pathGrid.Grid_Unsafe` 复制到自己的 `NativeArray<int>`，增量更新时只复制 dirty cells。

在 RimWorld 1.6 并行寻路下，推荐必须给 `PathFinderMapData` 注册或注入一个女仆专用 `CostSource`：

- 优点：更贴近原版 normal/fence/flying 的数据流。
- 优点：`PathGridJob` 读取的是稳定快照，避免直接读取 live `PathGrid.Grid_Unsafe`。
- 缺点：每张地图再增加约一个 path grid 的内存。
- 缺点：需要 `PathFinderMapData` 构造后注册 source，并保存 source 引用以供 `ParameterizeGridJob` 使用。

同时推荐注册 `ArtificialMaidConnectivitySource`，因为 1.6 的 `PathFinderJob` 依赖 connectivity 扩展邻格。

### 总体评估

方案 C 的主要性能成本是：

- 每张地图多一个 `PathGrid`、一个成本快照 source、一个连接图 source，内存约 `地图格子数 * 9 bytes`。
- 全图 path cost 重算时多一次全图遍历。
- `PathFinderMapData` full recompute 时多一份成本复制和一份女仆连接图计算。
- 单格 path cost dirty 时多一次单格计算。
- 女仆寻路时，A* 可能因为深水可通行而搜索更多格子。

它不会让普通 Pawn 的寻路持续变慢，只要补丁严格按 `ArtificialMaid` 过滤。和全局修改深水地形相比，方案 C 的性能影响更可控，也不会扩大到敌人、动物、普通殖民者的寻路。

最终建议：方案 C 可接受，但必须按 RimWorld 1.6 的并行寻路数据流实现。应把 `ArtificialMaidPathGrid.CalculatedCostAt(...)` 和 `ArtificialMaidConnectivitySource.ComputeCellConnectivity(...)` 写成零分配、无反射、少分支的热路径代码，并把深水成本设为较高值，避免女仆无意义地把海洋当作高速公路。

## 推荐实现顺序

1. 新增 `PathGridDef` 和 `ArtificialMaidPathGrid`。
2. 给 `ArtificialMaidDefOf` 加 `PathGridDef ArtificialMaidPathGrid`。
3. 新增 `ArtificialMaidCostSource` / `ArtificialMaidConnectivitySource` 的持有结构，并在 `PathFinderMapData` 构造后注册。
4. Patch `PathFinder.MapGridRequest.For`，给女仆请求加 marker customizer，避免 grid job 缓存混用。
5. Patch `PathFinderMapData.ParameterizeGridJob`，女仆请求使用 `ArtificialMaidCostSource.Data`。
6. Patch `PathFinder.ScheduleBatchedPathJobs` 和 `FindPathNow`，在 `mapData.ParameterizePathJob(ref job)` 后为女仆替换 `job.connectivity`。
7. Patch `Pawn.GetPathContext` 或 `Pathing.For(Pawn)`，保证实际移动阶段 `WalkableBy` 生效。
8. Patch `Pathing.For(TraverseParms)`，给带 pawn 的女仆请求返回专用 `PathingContext`。
9. Patch `Reachability.CanReach`，给女仆使用 cell-based reachability，避免原版 region cache 卡住深水。
10. Patch `Pawn_PathFollower.StartPath` 的 hardcoded `PassDoors` 预检查。
11. 保留或调整现有 `CostToMoveIntoCell` 补丁。

## 测试清单

- 在开发地图上生成一条 `WaterOceanDeep` 隔开的路径，命令 `ArtificialMaid` 去对岸，确认不显示 `NoPath`。
- 同样测试 `WaterDeep`、`ToxicWaterDeep`、`ToxicWaterOceanDeep`。
- 在深水上放墙/岩石/不可通过建筑，确认女仆不会穿墙。
- 测试门、禁用门、围栏、allowed area、forbidden 物品，确认没有绕过原版限制。
- 测试 drafted 和 undrafted 两种状态，因为原版水地形有 `extraDraftedPerceivedPathCost` / `extraNonDraftedPerceivedPathCost`。
- 测试保存/读档后继续寻路。
- 测试地形变化后 path cost 是否刷新，尤其是桥、浅水、深水之间切换。

## 最终建议

采用方案 C。

不要全局改水地形，也不要把女仆伪装成永久飞行 Pawn。RimWorld 1.6 的寻路链路中，深海水被 `PathGrid`、`Reachability`、`PathFinderMapData` 和 `Pawn_PathFollower.StartPath` 多处共同拦截；只改一个点会出现“能下达命令但找不到路”或“找到路但下一格不能走”的不完整行为。

推荐把能力定义为“ArtificialMaid 专用地形通行网格”，这样行为边界清楚，性能可控，对其他 Pawn 和地图系统影响最小。
